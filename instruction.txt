# Challenge Overview
Modern AI applications rarely depend on a single prompt. They often combine multiple steps such as model calls, tools, retrieval, validation, routing, and human approval.
These workflows can fail in unexpected ways:

An AI model may return incomplete or incorrectly formatted output
A tool or API may time out
Retrieved information may be missing
A workflow step may receive invalid input
A high-risk action may require human approval
A failed step may need a retry or fallback
This challenge is to build a browser-accessible AI Workflow Puzzle Builder where users solve interactive workflow puzzles by assembling AI-powered steps, testing the workflow, observing controlled failures, and improving the design using retries, fallbacks, validation, and human review.

The final product should feel like a visual puzzle and learning lab, not a production infrastructure platform or generic flowchart editor.
Users should be able to select a pre-seeded puzzle, understand its objective, assemble or modify the workflow, run it with sample input, trigger a controlled failure, repair the workflow, and review how reliably it performed.

# Challenge Goal

Build a fun and interactive AI workflow experience that allows users to:
Assemble multi-step AI workflows
Combine AI and deterministic steps
Run workflows using committed sample inputs
Trigger controlled failure scenarios
Add retries, validation, fallbacks, or human approval
Inspect each workflow step and its output
Receive feedback about the reliability of the final workflow
The goal is to help users understand how resilient AI applications are designed without requiring deep knowledge of production orchestration systems.

# Core User Journey

# A typical user journey should be:
● Select a pre-seeded workflow puzzle.
● Review the puzzle objective, input, expected result, and available blocks.
● Assemble or modify the workflow.
● Run the workflow under normal conditions.
● Inspect the result of each step.
● Enable a predefined failure scenario.
● Observe where and why the workflow failed.
● Add or configure a retry, fallback, validator, or human-review step.
● Run the workflow again.
● Review the execution trace and reliability feedback.

# The experience should use friendly puzzle language such as:

● Repair the broken workflow
● Survive the timeout
● Stop invalid data
● Add a safe fallback
● Ask a human before continuing
● Recover from the last successful step


# Functional Requirements
1. Visual Workflow Builder
The application must provide a browser-accessible interface where users can assemble or configure a multi-step AI workflow.
The builder should support a focused set of blocks or configurable steps, such as:

● Input
● AI model or prompt
● Tool or API
● Retrieval
● Condition
● Validator
● Retry
● Fallback
● Human review
● Output

Participants may use a drag-and-drop canvas, sequential step editor, configurable flow diagram, or another intuitive visual approach.


Constraints:
Users must be able to arrange, connect, or configure multiple workflow steps.
The complete workflow structure and step configuration must be visible before execution.


2. Pre-Seeded Workflow Puzzles
The platform must include 5 to 8 pre-seeded workflow puzzles organized by difficulty.

Each puzzle should include:
●  Puzzle title
● Difficulty level
● Objective
● Available workflow blocks
● Sample input
● Expected result or output format
● Failure scenario
● Completion criteria

Suggested difficulty levels:
Beginner
Intermediate
Advanced

# Constraints:
The puzzle set must include beginner, intermediate, and advanced experiences.
At least three puzzles must require users to handle or recover from a failure.

# Suggested Puzzle Set
Puzzle 1: Fix the Meeting Summarizer
Build a workflow that turns meeting notes into a summary, decisions, and action items while handling missing owners or malformed output.
Puzzle 2: Ground the Knowledge Assistant
Build a workflow that retrieves supporting information and refuses to answer when evidence is missing.
Puzzle 3: Repair the Ticket Router
Classify and route a customer ticket while handling missing categories or invalid confidence values.
Puzzle 4: Survive the Research Timeout
Combine information from multiple sources while handling a source or tool timeout.
Puzzle 5: Approve Before Sending
Draft an external message but require a human to approve, edit, or reject it before continuing.
Puzzle 6: Validate the Data Extractor
Extract structured information from unstructured text and recover when the AI returns invalid data.
Puzzle 7: Activate the Fallback
Retry a failed AI model call and switch to a fallback model or mock provider after repeated failures.
Puzzle 8: Resume the Interrupted Mission
Continue a workflow from its last successful step after a simulated interruption.
Participants may use different puzzle scenarios if they demonstrate equivalent learning objectives and reliability concepts.

3. Workflow Execution and Trace
The application must execute the configured workflow and show how information moves between its steps.

The execution experience should display:
● Current step
● Step status
● Step input
● Step output
● Validation result
● Error information
● Recovery action
● Final result

# Suggested step statuses include:
● Pending
● Running
● Completed
● Failed
● Paused
● Retrying
● Recovered
● Safely stopped
The execution trace should make the workflow understandable without requiring users to inspect backend logs.

# Constraints:
Users must be able to inspect the input, output, and status of every executed step.
The trace must record failures, retry attempts, fallback actions, validation results, and human decisions.


4. Failure Simulation and Recovery
The application must allow users to trigger predefined failures and configure how the workflow responds.

Supported failure scenarios may include:
● AI model timeout
● Tool or API timeout
● Invalid JSON
● Missing required field
● Schema validation failure
● Empty retrieval result
● Low-confidence output
● Tool failure
● Human approval rejection


# Supported recovery strategies may include:
Retry with a maximum number of attempts
Fallback model or tool
Repair invalid output
Use a safe default result
Route to human review
Stop safely with a clear error
Resume from the last successful step
Failure scenarios should be deterministic or repeatable so reviewers can consistently reproduce them.
Constraints:

The platform must support at least four distinct failure types.
Workflows must support retry, fallback, and explicit safe-failure behavior.


5. Validation and Human Review
The application must support output validation and human review as workflow control steps.

# A validator may check:
● Required fields
● Data types
● Allowed values
● Output format
● Confidence threshold
● Presence of supporting evidence

Validation may use JSON Schema, Zod, Pydantic, Valibot, or a custom validation approach.

# When validation fails, the workflow should be able to:
● Retry the step
● Repair the output
● Use a fallback
● Route the result for human review
● Stop safely with a clear explanation

# A human reviewer should be able to:
● Approve
● Edit
● Reject
● Resume or stop the workflow

# Constraints:
● At least one pre-seeded puzzle must require structured-output validation.
● At least one pre-seeded puzzle must pause and record a human decision before continuing.

6. Reliability Feedback and Local Demo Mode
After a workflow finishes, fails, or stops safely, the application must provide a clear reliability summary.
The feedback may consider:

● Whether the workflow completed successfully
● Whether the final output was valid
● Whether an injected failure was handled
● Number of retry attempts
● Whether a fallback was activated
● Whether human approval was used appropriately
● Whether any errors remained unhandled
● Whether the workflow stopped safely

The platform must include committed puzzle definitions, sample inputs, validation rules, failure configurations, and mock model/tool responses.
If a live AI provider is unavailable, users must still be able to run the seeded puzzles using a clearly labeled mock mode.

# Constraints:

Reliability feedback must identify successful recovery behavior and unresolved workflow weaknesses.
All pre-seeded puzzles must run locally without requiring paid AI or external API access.
